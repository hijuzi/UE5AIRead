# UE5 机制与调用链追踪

给定**一个机制名**，产出该机制的入口点、参与者、调用时序与数据流文档。

本技能是三个生产类技能里**最容易写出"看起来对但实际错"文档**的一个。
原因：调用链会被虚函数、委托、反射、多线程四条路径打断，静态搜索只能看到其中一条。
下面的约束就是针对这一点设计的。

## ⛔ 执行前置：源码必须完整（否则本技能不可执行）

本技能需要**函数实现体**。开工前先跑：

```powershell
(Get-ChildItem -Recurse -File -Filter *.cpp "<引擎源码根>" -ErrorAction SilentlyContinue).Count
```

**返回 0 时立即停止**，告知用户：

> 本机引擎是仅头文件安装（源码根下 0 个 `.cpp`），实现文件被剥离，无法追踪调用链。
> 可选方向：改用带完整源码的引擎版本，或在 Epic Launcher 中补装 Engine Source 组件。

**实测背景**：本机 2026-10-10 曾遇到 `HeadersOnly` 形态（`Engine/Source` 下 0 个 `.cpp`），
当时追踪 `StaticConstructObject_Internal` 只能找到声明、找不到实现体，调用链完全无法追。
重装补齐源码后为 13,182 个 `.cpp`，技能恢复可用。

> `Engine` 目录下另有 327 个 `.cpp` 属于 Marketplace / Fab / Bridge 等**用户插件**，
> 与引擎源码无关。`check-source.ps1` 已把它们排除——不排除的话会被误判成 `Complete`。

**不要在只有头文件的情况下"追"调用链。** 那只能产出一篇基于常识推测、
无法被 `ue-doc-verify` 回查的伪文档，比不产出更糟。

## 职责边界

| 本技能负责 | 本技能**不做** |
|---|---|
| 一个机制的入口点与终点 | 类型的字段级细节与完整 API（→ `ue-type-api`） |
| 跨类的调用顺序与参与者 | 模块的目录与依赖（→ `ue-module-structure`） |
| 数据在链路上的传递与变换 | 逐行解释函数实现 |
| 链路上的扩展点与分支条件 | 性能优化建议 |

**判断标准**：如果内容不需要跨越两个以上类型就能讲完，它应该属于 `ue-type-api`。
反过来，一旦讲的是"先发生什么、后发生什么、谁触发的"，就是本技能。

## 前置条件

`docs/_meta/convention.md` 与 `docs/_meta/inventory.md` 必须存在。
涉及的模块最好已有 `docs/modules/<模块>-结构.md`，涉及的类最好已有 `docs/types/<类>.md`
——本技能会大量交叉引用它们。

## 核心约束（五条，第一条最关键）

1. **必须先声明"追踪边界"，再写内容。** 没有边界声明的调用链文档，会被读成"这就是全部流程"。
   边界声明包含四项，写进产物开头：

   | 项 | 说明 |
   |---|---|
   | 入口点 | 从哪个函数／事件开始追 |
   | 终止条件 | 追到哪一层停（如"停到叶子实现，不再追其内部"） |
   | 深度上限 | 最多展开几层 |
   | **未覆盖的分支** | 哪些分支本次没追（平台分支、编辑器分支、异步分支） |

2. **每一步都要有引用。** 调用链上的每一跳都必须给"文件 + 行号区间"。
   没有引用的调用顺序就是猜测，`ue-doc-verify` 会逐条回查。

3. **区分四种调用类型，不能混写成一条线：**

   | 类型 | 特征 | 静态搜索能否找到 | 文档中如何标注 |
   |---|---|---|---|
   | 直接调用 | `Foo->Bar()` | ✅ 能 | 直接写调用 |
   | 虚函数分派 | 基类调虚函数，实际执行子类 | ⚠️ 只能找到基类声明 | **列出已知实现**，或明确写"实现类未知，需按实际类型判断" |
   | 委托 / 回调 | `Delegate.Broadcast()` / `AddUObject` | ❌ 找不到绑定关系 | **列出绑定点的位置**，没有绑定比"不写"更糟 |
   | 反射 / 蓝图调用 | 通过 `UFunction` 名字、`ProcessEvent` | ❌ 完全找不到 | **必须显式标注"此跳为反射调用，静态搜索不可见"** |

   > 把虚函数分派写成直接调用，是本文档类型最常见的错误。

4. **只读。** 不修改引擎任何文件。写入仅限 `docs/flows/`。
   用户要求"改流程 / 改行为 / 给补丁"时：**拒绝，且不得给出可直接应用的引擎源码补丁或写操作建议**；
   若其真实意图是理解现状，回到只读追踪（产出或更新流程文档）。
5. **引用要能被 token 解析。** 调用链文档的引用密度最高，三类写法会被 `ue-doc-verify` 判为"引用缺失"，
   必须规避：模块内相对形式（如 `Engine/Classes/...`）、用 `.../` 缩写中间段、
   路径后紧跟全角括号不设分隔。写完后自查这三条；规则原文见 `_meta/convention.md` 第 4.1 节。

## 执行步骤

### Step 1: 定义追踪边界（不要跳过）

在开始搜索**之前**，先把四项边界写下来。这一步不产出文档内容，但它决定后面每一步的取舍。

用户只给了机制名（如"UObject 创建流程"）时，边界由你根据以下规则确定并**告知用户**：

- **入口点**：优先选用户能直接调用的公开 API（`NewObject`、`SpawnActor`），而不是内部函数
- **终止条件**：默认"停到叶子实现"，即追到不再调用其他引擎函数的那一层
- **深度上限**：默认 5 层。超过后只列函数名与位置，不展开其内部
- **未覆盖分支**：默认只追**默认配置 + 当前平台**的主路径。平台分支、编辑器分支、异步路径
  标注出来但不展开——**但必须在产物里写明"未覆盖"**

**检查点**：能回答"从哪开始、到哪结束、哪些不追"。答不上就先问用户，不要开搜。

### Step 2: 定位入口点

用两步定位，不要直接全库搜：

1. **在已有产物里找线索**：`docs/types/` 与 `docs/modules/` 里往往已有相关类型与模块的文档，
   先用它们缩小范围
2. **在候选模块内搜索入口函数名**：

```
search_content: pattern="<入口函数名>" glob="*.h" path="<候选模块路径>"
```

**检查点**：入口点必须命中**函数定义或声明**，而不是注释或字符串。命中在注释里时换更精确的模式。

### Step 3: 逐层展开调用链

对每一层，按顺序做四件事：

1. 读当前函数的实现体
2. 记录它调用了哪些函数（**分开记**：直接调用 / 虚函数 / 委托 / 反射）
3. 对每个下游函数，判断是否已达终止条件（叶子实现）
4. 未达终止条件的，进入下一层

**记录格式**（内部工作用，不必写进产物）：

```
[L1] Foo::Bar()            Engine/Source/.../Foo.cpp 行 120-145
  ├─ [直接] Baz::Qux()      Engine/Source/.../Baz.cpp 行 88
  ├─ [虚]   Foo::OnThing()  Engine/Source/.../Foo.cpp 行 160   → 实现类：A/B/C
  └─ [委托] OnDone         绑定于 Engine/Source/.../Foo.cpp 行 200
```

**检查点**：
- 每一层结束时，检查是否出现**环**（A→B→A）。出现环时记录环并停止该分支，**不要无限展开**
- 层数达到深度上限时，停止展开并在产物中标注"已截断"

### Step 4: 梳理数据流

调用链只说明"谁调用谁"，还需要说明"数据如何流动"：

| 要记录 | 说明 |
|---|---|
| 输入 | 入口点接收的参数、全局状态、配置 |
| 变换点 | 数据在哪些环节被改写（含关键的默认值填充） |
| 输出 | 最终产出（新对象、写回的字段、副作用） |
| 全局状态变更 | 改动了哪些全局单例／子系统 |

### Step 5: 写产物

路径：`docs/flows/<机制名>.md`，机制名用中文描述性名称（如 `UObject创建流程.md`）。

````markdown
> 引擎版本：<从 docs/_meta/convention.md 复制>
> 源码根：Engine/Source
> 生成技能：ue-flow-trace v1.0
> 生成时间：YYYY-MM-DD
> 校验状态：未校验

# <机制名>

## 一、追踪边界

| 项 | 本次范围 |
|---|---|
| 入口点 | `函数名()` @ `Engine/Source/...` |
| 终止条件 | |
| 深度上限 | N 层 |
| 未覆盖分支 | 平台分支 / 编辑器分支 / 异步路径（逐项列出） |

## 二、机制概述

三到五句话说明这个机制做什么、为什么存在、谁会用。

## 三、参与者

| 类型 / 类 | 所属模块 | 在链路中的角色 |
|---|---|---|

## 四、调用时序

按层次展开。每一跳标注调用类型（直接 / 虚函数 / 委托 / 反射）。

```
[1] 入口
    └─ 直接 → ...
        ├─ 虚   → ...        （实现类：...）
        └─ 委托 → ...        （绑定点：...）
```

## 五、数据流

输入 → 变换点 → 输出，以及全局状态变更。

## 六、扩展点

链路上可被游戏代码介入的位置：可覆写虚函数、可绑定的委托、可替换的工厂。

## 七、关键分支与条件

主路径之外的重要分支及其生效条件。本次未展开的，写明"未覆盖"。

## 相关文档

- （链接到相关的 types/ 与 modules/ 产物）
````

**检查点**：

```powershell
Test-Path "docs\flows\<机制名>.md"
Select-String -Path "docs\flows\<机制名>.md" -Pattern '追踪边界' -Quiet
Select-String -Path "docs\flows\<机制名>.md" -Pattern '未覆盖分支' -Quiet
```

三条都要通过。**没有「追踪边界」章节的流程文档视为不合格。**

### Step 6: 交回主技能

告知用户：产物路径、链路层数、被截断的分支数、未覆盖的分支数。
**由主技能更新 `docs/00-索引.md`。**

## 输出示例

**示例 1：正常路径**

输入：`UObject 的创建流程是怎么走的`

应做：Step 1 定边界（入口 `NewObject`，终止到叶子实现，深度 5 层，不追平台分支）
→ Step 2 在 `CoreUObject` 内定位入口
→ Step 3 逐层展开，分开记直接/虚/委托/反射调用
→ Step 4 梳理 `FObjectInitializer` 的数据变换
→ Step 5 写产物 → Step 6 交回。

**示例 2：机制名太宽（边界）**

输入：`UE 的渲染流程`

应做：渲染流程跨越数十个类、多个线程、多帧。**不要直接开追**——
把机制拆成可追踪的子流程让用户选，例如"RHI 命令提交""渲染线程帧调度""着色器编译"。

不应做：硬追一个横跨上千个函数的"流程"，产出一篇没有边界、无法校验的文档。

**示例 3：机制不存在（异常）**

输入：`UE 的 XXX 流程`

应做：在候选模块内搜索无命中 → 告知用户本引擎里没有对应机制，提示是否拼错或是否是项目自己实现的。

不应做：凭对 UE 的一般印象编造一条调用链；也**不得产出任何 `docs/flows/` 文件**——
无中生有的产物比没有更糟（下游会把空文档当成事实）。

**示例 4：链路被反射打断（边界）**

应做：追到 `ProcessEvent` 或 UFunction 名字调用时，**显式标注"此跳为反射调用，静态搜索不可见"**，
并列出可静态确认的部分（如 UFunction 的注册位置）。

不应做：跳过这一跳、或假装它是直接调用。

## 常见问题

### Q: 追到多深才算合适？

看读者。给写 Gameplay 代码的人看，追到"能判断该覆写哪个函数"就够；
给做引擎改造的人看，可以更深。默认 5 层是折中值——
**关键不是深度，而是把边界写清楚**，让读者知道往下还有东西。

### Q: 遇到 `check()` / 断言分支要追吗？

不追。断言是防御性代码，不是机制的一部分。但如果断言揭示了前置条件（如"必须在游戏线程调用"），
把它记进「数据流」或「关键分支」章节——这类信息对使用者价值很高。

### Q: 一个机制在不同平台差异很大，怎么办？

按 `convention.md` 的环境锁定（本机 UE 5.8 on Windows）追主路径，
在「追踪边界」的「未覆盖分支」里明确列出其他平台分支的存在与位置。
**不要**试图在一篇文档里覆盖所有平台——那会得到一篇谁都用不上的文档。

### Q: 调用链里出现了我不认识的第三方库函数，要追吗？

不追。记下函数名与位置，标注"第三方实现，不在本套件范围内"即可。
本套件只覆盖引擎自身的 `Runtime` / `Plugins` 白名单。
