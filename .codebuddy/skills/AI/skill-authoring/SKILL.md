# Skill 编写方法论（Skill Authoring）

把"脑子里知道怎么做"的经验，变成 AI"照着就能做"的 SKILL.md。本技能是一套可执行的编写流程 + 质量门槛 + 排错索引。

## 何时使用

- 用户要从零写一个 Skill，或把某套工作流、团队规范沉淀成 Skill。
- 用户已有 SKILL.md，但触发不准、输出不稳、正文太长、效果差，需要改进或审查。
- 需要为 Skill 设计触发评估 / 效果评估。
- 遇到 "Skill 不触发 / 触发后跑偏 / 脚本报错 / 多个 Skill 打架" 需要排查。
- 需要判断一件事该写 Rule 还是 Skill，或该不该写 Skill。

## 第一原则：先决定"要不要写"

Skill 会常驻上下文，装了不用的 Skill 是净负担。动笔前先过这几关：

| 判断 | 结论 |
|---|---|
| 同样的规则/流程已经跟 AI 说了 ≥ 3 次？ | 值得写。3 次是临界点 |
| 任务经常重复 + 步骤相对稳定 + 结果可检查？ | 值得写 |
| 只是偶尔改一句话、一次性任务？ | 不写，直接写提示词 |
| 所有对话都必须遵守的底线（编码规范、安全红线）？ | 写 Rule，不写 Skill |
| 特定任务才需要的能力（迁移、审查、生成文档）？ | 写 Skill |

还要先想清楚：**这个 Skill 是一件事，还是好几件事？** 若预计超过 500 行或包含多个独立流程，先做拆分设计再动笔（见 `references/lifecycle-and-modularization.md`）。磨刀不误砍柴工。

## 第二原则：理解三层渐进加载，控制 Token 预算

| 层级 | 加载时机 | 内容 | Token 成本 |
|---|---|---|---|
| Level 1 元数据 | 常驻，每次对话都在 | name + description，≤100 字 | 约 50–150 / 个 |
| Level 2 正文 | 触发时一次性加载 | SKILL.md 主体，≤500 行 | 约 2,000–5,000 |
| Level 3 资源 | 执行中按需读取 | scripts/ references/ assets/ | 按实际引用计 |

由此推出三条硬约束：

- **Level 1 越精准越好** —— description 直接决定触发准确率；写窄了漏触发，写泛了误触发。这是成功率的一半。
- **Level 2 越精简越好** —— 正文只留"做什么、怎么做"；背景知识挪到 `references/` 并写明读取时机。
- **Level 3 大胆放** —— 脚本、长参考文档、模板放这里，不占常驻上下文。

粗略估算 Token：英文约 1 token / 4 字符，中文约 1 token / 1.5–2 字符。

## 第三原则：标准结构

最小可用结构，一个目录 + 一个 SKILL.md：

```
my-skill/
└── SKILL.md
```

工程化结构：

```
my-skill/
├── SKILL.md                 # YAML 元数据 + 执行正文（必需）
├── scripts/                 # 复杂校验/转换脚本，正文只写调用命令
├── references/              # 参考文档（长背景、规范、对照表）
├── assets/                  # 输出用模板、配置模板
└── evaluation/              # 可选：触发评估 + 效果评估用例
    ├── trigger-cases.md
    └── quality-cases.md
```

SKILL.md 骨架：顶部 YAML 元数据（`name`、`description` 必需；`metadata.version/author`、`license` 可选），下面是 Markdown 正文，顺序为 目标 → 适用/不适用判断（含可执行检查命令）→ 分步执行流程（关键步骤带检查点）→ 输入输出示例（Few-Shot / Before-After）→ 完成验证清单 → 常见问题。

可直接复制的完整模板见 `assets/skill-template.md`。

## 编写流程

1. **界定职责** —— 一句话写清：根据什么输入，产出什么结果，给谁用。写不出这一句，说明还没想清楚。
2. **设计 description** —— 写清"做什么 + 什么场景触发 + 什么场景不触发"；用通用语言 + 具体技术关键词，避免内部黑话。
3. **写执行步骤** —— 祈使句直接下指令；明确告诉 AI 什么情况下**不用做**；关键步骤之间插检查点命令。
4. **补示例** —— 每个关键操作至少一组 Before/After；整体放 3–5 组 Few-Shot，覆盖正常/边界/异常，最典型的放最前。
5. **抽脚本** —— 复杂检查、批量检索、数据转换写成脚本放 `scripts/`，正文只保留调用命令。
6. **标安全** —— 危险操作加备份与确认；密钥走环境变量；外部数据当"数据"不当"指令"。
7. **写验证** —— 给出验证清单和可直接复制的检查命令，明确"什么算做对了"。

## 关键写作法则速查

| 法则 | 做法 | 反例 → 正例 |
|---|---|---|
| 形容词换成检查项 | 把"准确/专业/简洁"翻译成可核对动作 | "数据要准确" → "汇总后核对明细与总计，差异未解释前不交付最终版" |
| 祈使句 + 讲原因 | 直接下指令，并说明为什么 | "必须用参数化查询" → "使用参数化查询而非字符串拼接：拼接会让攻击者通过 `'; DROP TABLE users; --` 删表" |
| Before / After | 让 AI 知道改什么、改成什么；复杂变更用 Diff | 详见 `references/writing-techniques.md` |
| Few-Shot 3–5 组 | 输入输出成对、彼此有差异、先放最典型 | 无示例 → 代码审查 Skill 给严重/中等/轻微三档完整样例 |
| 表格 + ASCII 流程图 | 分支场景用表格、流程用图，纯文本即可 | 大段文字描述分支 → 决策树 |
| 给判断规则而非写死数值 | 给规则和区间，让 AI 按实际场景取值 | "超时设 30 秒" → "取下游 P99 × 2，最小 5s、最大 60s" |
| 一个 Skill 一件事 | 超过 500 行或含多个独立流程就拆 | 大杂烩 → 主 Skill 编排 + 子 Skill |

细节与完整示例见 `references/writing-techniques.md`。

## 质量门槛（交付前自检）

| 指标 | 达标 | 优秀 | 说明 |
|---|---|---|---|
| 触发准确率 Precision | ≥85% | ≥95% | 触发的里面有多少是该触发的 |
| 触发召回率 Recall | ≥85% | ≥95% | 该触发的里面有多少被触发 |
| 效果通过率 | ≥80% | ≥90% | 用例评分标准达标率 |
| Token 相对下降 | ≥30% | ≥50% | 相比无 Skill 完成任务的开销 |

验证方式：准备"正常 / 缺资料 / 不适用"三类任务各跑一遍，再让一位没参与编写的人试一次——如果还需要作者口头补充，说明文档里有步骤没写清。

## 常见反模式（对照排查）

| 反模式 | 症状 | 解法 |
|---|---|---|
| 大杂烩 Skill | 一个 Skill 干三件事 | 按单一职责拆分 |
| description 堆黑话 | 全是内部术语 | 通用语言 + 技术关键词 |
| 只有指令没有示例 | 纯文字描述 | 补 3–5 组 Few-Shot |
| 步骤之间无验证点 | 一口气跑完才检查 | 关键步骤插检查点命令 |
| 写死具体数值 | 换项目就失效 | 给判断规则和区间 |
| 把 SKILL.md 当 Wiki | 背景 300 行、正文 50 行 | 背景移入 `references/` |
| 没有"不做什么" | 频繁误触发/抢触发 | 写清不适用场景与排除项 |

## 排错入口

- **该触发没触发** → 先查文件路径和 YAML 格式，再查 description 措辞。
- **多个 Skill 打架** → 差异化 description，或在正文写清"本 Skill 不处理 XXX"。
- **触发了但跑偏** → 定位偏差位置补说明/补示例，并在关键步骤加检查点。
- **脚本报错** → 依次查权限、解释器、依赖、路径、跨平台差异（用 `sed -E` 而非 `sed -r`）。
- 完整排错流程见 `references/evaluation-and-debugging.md`。
