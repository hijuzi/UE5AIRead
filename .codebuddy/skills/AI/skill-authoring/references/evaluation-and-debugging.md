## 1. 验证清单与验证命令

别光写不验证。每个 Skill 都应有可勾选的验证清单，并配上能直接复制粘贴跑的命令。

```markdown
## 验证清单

### 功能验证
- [ ] 所有旧版 import 路径已替换
- [ ] 新版客户端模块已添加到 go.mod
- [ ] 旧版客户端模块已从 go.mod 移除
- [ ] `go vet ./...` 无警告

### 构建验证
- [ ] `go build ./...` 编译正常
- [ ] `go test ./...` 全部通过
- [ ] 编译产物中不包含旧包引用

### 运行验证
- [ ] 核心接口请求正常
- [ ] 错误处理逻辑正常
- [ ] 超时和重试机制正常
```

配套脚本：

```bash
echo "=== 检查旧版引用 ==="
grep -rn "old-http-client" . --include="*.go" \
  && echo "❌ 仍有旧版引用" || echo "✅ 旧版引用已清理"

echo "=== Go 静态检查 ==="
go vet ./... && echo "✅ 静态检查通过" || echo "❌ 静态检查失败"

echo "=== 单元测试 ==="
go test ./... && echo "✅ 测试通过" || echo "❌ 测试失败"

echo "=== 编译检查 ==="
go build ./... && echo "✅ 编译通过" || echo "❌ 编译失败"
```

**通用三步验证**（不只适用于代码类 Skill）：准备"正常任务 / 缺资料任务 / 不适用任务"三类各跑一遍——

| 测试 | 怎么试 | 重点看什么 |
|---|---|---|
| 正常任务 | 给一套完整资料 | 是否按要求交付，结果能否核对 |
| 缺资料任务 | 故意缺关键字段或文件 | 是否正确询问或说明缺口，而非编造 |
| 不适用任务 | 给一个相近但不属于此 Skill 的请求 | 是否避免强行套用流程 |

最后请一位没参与编写的同事再试一次。**如果还需要作者反复口头补充，说明文档里有关键步骤没写清。**

## 2. 评估方法与指标

推荐流程：

1. **准备测试用例** —— 正常和边界情况都要有，多搞几组。
2. **对比跑一下** —— 有 Skill 和没 Skill 各跑一遍，看差距。
3. **定义通过标准** —— 每个用例怎么算"通过"，提前约定。
4. **看数据** —— 通过率、Token 消耗、耗时。
5. **根据结果调整** —— 哪里不行改哪里，再跑一轮。

```
评估循环：
  编写/修改 Skill → 运行测试用例 → 评估结果 → 优化 Skill → 重复
                                    ↓
                         满意 → 扩大测试规模 → 正式发布
```

指标与参考目标：

| 指标 | 说明 | 达标线 | 优秀线 |
|---|---|---|---|
| 触发准确率 Precision | 触发的里面有多少是该触发的 | ≥85% | ≥95% |
| 触发召回率 Recall | 该触发的里面有多少被触发 | ≥85% | ≥95% |
| 效果通过率 | 用例评分标准达标率 | ≥80% | ≥90% |
| Token 相对下降率 | 相比无 Skill 完成任务的开销 | ≥30% | ≥50% |
| 输出一致性 | 同输入多次执行输出的相似度 | >85% | — |

> 不需要每个指标都精确测量。**优先盯触发准确率与效果通过率**，这两项直接决定 Skill 是否可用。

## 3. 触发评估

触发评估回答的是：**description 写得好不好？** 构造三类用例：

| 用例类型 | 说明 | 示例（Go 单测生成 Skill） |
|---|---|---|
| 正例（应触发） | 用户意图确实匹配 | "帮我写个单元测试"、"给 Add 函数补个 test"、"生成表驱动测试" |
| 反例（不应触发） | 意图与 Skill 无关 | "帮我写个 README"、"优化这段代码的性能"、"部署到生产环境" |
| 边界用例（模糊意图） | 可能匹配也可能不匹配 | "帮我检查一下这个函数"、"这段代码质量怎么样" |

规模：正例 10–20 条、反例 10–20 条、边界若干。逐条模拟提问并记录是否触发，输出报告：

```
=== 触发评估报告 ===
Skill: go-test-gen
测试用例数: 30 (正例 15, 反例 12, 边界 3)

📊 触发准确率 (Precision): 93.3%  ✅
   正确触发 14/15, 误触发 1/12

📊 触发召回率 (Recall): 93.3%  ✅
   正确触发 14/15, 漏触发 1/15

❌ 漏触发用例:
   - "帮我补充一下 math.go 的 test coverage"
     → 建议在 description 中补充 "coverage"、"补充测试" 等关键词

⚠️ 误触发用例:
   - "帮我测试一下部署脚本能不能跑通"
     → 建议在 description 中明确排除"运行测试"和"集成测试"场景

🟡 边界用例分析:
   - "帮我检查一下这个函数" → 未触发 (合理)
   - "这个函数需要测试吗" → 触发 (合理)
```

按报告针对性改 description，再跑一轮，直到达标。

## 4. 效果评估

触发准只是第一步，**输出质量**才是最终目标。每个测试用例包含三部分：**输入**（提问 + 上下文）、**预期输出**、**评分标准**。

````markdown
## 测试用例 1：简单函数

**输入**：为以下函数生成单元测试

```go
func Max(a, b int) int {
    if a > b {
        return a
    }
    return b
}
```

**评分标准**：
- [ ] 使用表驱动模式（t.Run + 结构体切片）
- [ ] 覆盖 a > b、a < b、a == b 三种情况
- [ ] 不引入第三方测试框架
- [ ] 测试函数命名为 TestMax
- [ ] 生成的代码可直接编译运行

## 测试用例 2：包含错误返回的函数

**输入**：为以下函数生成单元测试

```go
func Divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, fmt.Errorf("division by zero")
    }
    return a / b, nil
}
```

**评分标准**：
- [ ] 覆盖正常除法和除零两种场景
- [ ] 除零场景检查 error 不为 nil
- [ ] 正常场景检查 error 为 nil 且结果正确
- [ ] 浮点比较使用合理的精度容差
````

在"有 Skill"和"无 Skill"两种条件下分别执行，输出对比报告：

```
=== 效果评估报告 ===
Skill: go-test-gen
测试用例数: 5

📊 总体通过率: 88.0% (有 Skill) vs 52.0% (无 Skill)
📊 Token 消耗: 平均 1,200 Token/用例 (有 Skill) vs 2,100 Token/用例 (无 Skill)

逐用例评分:
┌──────────────┬──────────────┬──────────────┬───────────┐
│ 用例         │ 有 Skill     │ 无 Skill     │ 提升幅度  │
├──────────────┼──────────────┼──────────────┼───────────┤
│ 简单函数     │ 5/5 ✅       │ 3/5          │ +40%      │
│ 错误返回     │ 4/5 ✅       │ 2/5          │ +40%      │
│ 多返回值     │ 5/5 ✅       │ 3/5          │ +40%      │
│ 接口方法     │ 4/5 ✅       │ 2/5          │ +40%      │
│ 并发场景     │ 4/5 ⚠️       │ 3/5          │ +20%      │
└──────────────┴──────────────┴──────────────┴───────────┘

⚠️ 薄弱环节:
  - 用例 "错误返回": 浮点比较未使用精度容差 → 建议在 Skill 中补充浮点测试示例
  - 用例 "并发场景": 缺少 race condition 检测 → 建议增加 `go test -race` 验证步骤
```

## 5. 评估用例的持久化

评估不是"做一次就完事"。把评估用例作为 Skill 的固定资产一起维护：

```
my-skill/
├── SKILL.md
├── scripts/
├── references/
└── evaluation/
    ├── trigger-cases.md   # 触发评估：正例 + 反例 + 边界
    └── quality-cases.md   # 效果评估：输入 + 评分标准
```

什么时候重跑：

| 变更类型 | 重跑触发评估 | 重跑效果评估 |
|---|---|---|
| 修改了 description | ✅ | — |
| 修改了步骤或示例 | — | ✅ |
| 新增场景分支 | ✅ | ✅ |
| 只修了错别字 | ❌ | ❌ |

**核心原则：区分"指令"与"数据"。**

> 如果 Skill 是团队共享的：建议 PR Review 时要求附带评估报告。就像代码变更要跑单测一样，Skill 变更也应跑评估——这就是"Skill 的单元测试"。修改 description 后，若触发指标仍不达标，先别急着放弃，检查是否存在与其他 Skill 的语义冲突。

## 6. 调试与排错指南

### 6.1 AI 该触发却没触发

排查顺序：

```
Skill 没触发
     ↓
1. Skill 加载了吗？ ──── 没有 → 检查文件路径和目录结构
     ↓ 加载了
2. Description 匹配吗？ ──── 不匹配 → 调整 description 措辞
     ↓ 匹配
3. 是否被其他 Skill 抢了？ ──── 是 → 检查多个 Skill 的 description 是否冲突
     ↓ 否
4. 用户提问措辞太模糊？ ──── 是 → 在 description 中补充更多触发关键词
```

检查方法：

```bash
# 确认文件存在且路径正确
ls -la ~/.codebuddy/skills/my-skill/SKILL.md

# 确认 YAML 头格式正确（常见问题：缩进错误、缺少 ---）
head -10 ~/.codebuddy/skills/my-skill/SKILL.md
```

常见原因：

| 原因 | 表现 | 解决方法 |
|---|---|---|
| 路径放错 | Skill 根本没被加载 | 确认放在用户级或项目级 skills 目录下 |
| YAML 格式错误 | 开头 `---` 缺失或缩进不对 | 用 YAML 校验工具检查 |
| description 太笼统 | AI 不确定该不该触发 | 加入具体关键词和使用场景 |
| description 太窄 | 只有精确匹配才触发 | 补充同义词和常见表述 |

### 6.2 多个 Skill 冲突

症状：AI 总是触发错的那个，或把两个 Skill 的指令混在一起执行。原因是多个 description 语义重叠（如"Go 代码审查" vs "Go 安全扫描"，用户说"帮我检查一下这段代码"时两者都可能触发）。

| 策略 | 做法 | 适用场景 |
|---|---|---|
| 差异化 description | 让每个 Skill 有明确的区分关键词 | 功能部分重叠 |
| 合并为一个 | 经常一起触发就合并 | 高度相关 |
| 添加排斥说明 | 正文显式写"本 Skill 不处理 XXX" | 容易被误触发 |
| 手动指定 | 对话中明确指定用哪个 | 需要精确控制 |

正文写法：

```markdown
## 适用范围

本 Skill 专注于**代码安全漏洞扫描**（SQL 注入、XSS、硬编码凭据等）。

以下场景不在本 Skill 范围内：
- 代码风格和命名规范 → 使用 `go-code-review` Skill
- 性能优化建议 → 使用 `go-perf-review` Skill
```

> 经验法则：如果两个 Skill 的触发准确率都低于 80%，先检查是不是 description 有冲突。**把"什么不做"写清楚，往往比把"做什么"写详细更有效。**

### 6.3 触发了但执行偏了

1. **先看指令是否不够明确** —— 把 AI 输出与 SKILL.md 逐条对比，哪里偏了就在哪补更具体的说明或示例。
2. **检查是否缺少示例** —— 格式不对就补格式示例；遗漏某种情况就补覆盖该情况的示例。
3. **检查是否指令冲突** —— 正文前后是否矛盾；多个 Skill 是否给了互相矛盾的指令。

实用技巧：在关键步骤后加"检查点"，让 AI 自我验证。

````markdown
## Step 2: 替换 import 路径

将所有 `old-http-client` 的 import 替换为 `unified-httpclient`。

**检查点**：替换完成后运行以下命令确认没有遗漏：

```bash
grep -rn "old-http-client" . --include="*.go"
```

如果仍有输出，说明有遗漏，继续处理。
````

### 6.4 脚本执行报错

| 报错类型 | 典型信息 | 解决方法 |
|---|---|---|
| 权限不够 | `Permission denied` | `chmod +x scripts/pre-check.sh` |
| 解释器不对 | `bad interpreter` | 检查 shebang 行（`#!/bin/bash`）路径 |
| 依赖缺失 | `command not found` / `ModuleNotFoundError` | 前置条件里列明依赖并给安装命令 |
| 路径问题 | `No such file or directory` | 用相对 Skill 目录的路径，或脚本开头 `cd` |
| 平台不兼容 | macOS / Linux 命令差异 | 用 `sed -E` 而非 `sed -r`；Windows 改用 `.ps1` |

防御性写法：

```bash
#!/bin/bash
set -euo pipefail

for cmd in go grep sed; do
  if ! command -v "$cmd" &> /dev/null; then
    echo "❌ 缺少必要命令: $cmd，请先安装"
    exit 1
  fi
done

if [ ! -f "go.mod" ]; then
  echo "❌ 请在项目根目录执行此脚本"
  exit 1
fi
```

### 6.5 通用调试方法论

```
1. 确认 Skill 已加载   → 路径对不对、格式有没有错
2. 确认触发正确        → Description 是否匹配用户意图
3. 确认指令清晰        → 逐步检查 AI 输出与预期的偏差点
4. 确认脚本可执行      → 权限、依赖、路径、平台兼容性
5. 加检查点缩小范围    → 关键步骤之间插入验证命令
6. 对比测试定位问题    → 有 Skill vs 无 Skill，看差异在哪
```

> 经验之谈：大多数问题（估计 70% 以上）出在前两步——要么没加载成功，要么 description 不够好导致没触发。先查这两个能省很多时间。

## 7. 反模式详解

| 反模式 | 表现 | 问题 | 正确做法 |
|---|---|---|---|
| **大杂烩 Skill** | 一个 Skill 里塞了三四件不相关的事 | AI 张冠李戴；正文超 1000 行，Token 飙升 | 一个 Skill 一件事；有关联就拆成主 + 子 Skill |
| **Description 写成内部黑话** | `处理 TCC 的 v3 迁移，适配 QCMS 的新规范` | AI 不知道 TCC、QCMS 是什么，无法匹配 | 通用语言描述功能，辅以具体技术关键词 |
| **只有指令，没有示例** | 全是"做这个、做那个"的文字 | 输出格式和细节全靠猜 | 每个关键操作至少配一个 Before/After |
| **步骤之间没有验证点** | 列 5 步，一口气做完才检查 | 错误被放大，排查困难 | 关键步骤间插入检查点命令 |
| **写死具体数值** | "超时设为 30 秒""缓冲区 4096" | 换项目就不对，AI 死搬硬套 | 给判断规则和参考范围（如 P99 × 2） |
| **SKILL.md 当 Wiki 写** | 300 行背景，50 行正文 | 有效指令被噪音淹没，遵循率下降 | 背景放 `references/`，正文只留做什么/怎么做 |

速查表：

| 反模式 | 一句话症状 | 解法 |
|---|---|---|
| 大杂烩 Skill | 一个 Skill 干三件事 | 拆分 |
| Description 黑话 | 全是内部术语 | 通用语言 + 技术关键词 |
| 没有示例 | 纯文字描述 | 加 Few-Shot |
| 没有验证点 | 做完才检查 | 关键步骤加检查点 |
| 写死数值 | 硬编码配置 | 给判断规则和区间 |
| 当 Wiki 写 | 背景 300 行正文 50 行 | 背景放 `references/` |

### 交付前完整检查清单

**内容**
- [ ] 目标明确：做什么、为什么做、什么时候触发
- [ ] Description 精准，且在合适时机能自动匹配
- [ ] 用祈使句直接下指令，并解释了原因
- [ ] 有 3–5 组 Before/After 或输入输出示例
- [ ] 覆盖多种场景，有决策树或分支处理
- [ ] 易错点和注意事项已标注
- [ ] 有验证清单和能跑的检查命令

**结构**
- [ ] YAML 元数据完整（name、description）
- [ ] 正文 ≤500 行，超出已模块化拆分
- [ ] 依赖明确（前置条件、相关 Skill）
- [ ] 善用表格、ASCII 流程图组织信息

**工程与安全**
- [ ] 版本号合理，变更可追溯
- [ ] 子 Skill 脱离主流程也能跑
- [ ] 无硬编码密钥；危险操作有确认或备份
- [ ] 脚本输入有校验；路径无未验证拼接
- [ ] 网络请求用 HTTPS 并设置合理超时
- [ ] 关键步骤有检查点，不是一口气跑完才验证
