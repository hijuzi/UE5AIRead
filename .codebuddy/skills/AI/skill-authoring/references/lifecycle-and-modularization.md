## 1. 什么时候该拆

出现以下任一情况就该考虑拆分：

- 文件写着写着超过 500 行（建议上限）
- 包含多个可独立的工作流程
- 有些步骤可以单独用，没必要每次跑整个 Skill
- 不同部分改动频率差很多（一个一个月改三次，另一个半年不动）

## 2. 拆成什么样

**简单场景：一个文件搞定**

```
my-skill/
└── SKILL.md
```

**复杂场景：主 Skill + 子 Skill**

```
project-migration/                  # 主 Skill：流程总览与编排
├── SKILL.md
└── steps/                          # 拆分出的子步骤文档，主 SKILL.md 按顺序引用
    ├── 00-environment-setup.md
    ├── 01-dependency-update.md
    └── 02-api-migration.md

project-migration-sub-env-setup/    # 子 Skill：可独立调用
├── SKILL.md
└── scripts/
    └── check-env.sh

project-migration-sub-api-migrate/  # 子 Skill：可独立调用
├── SKILL.md
└── references/
    └── api-mapping.json
```

另一种组织方式：不建独立子 Skill，只在主 Skill 下用 `references/` 承载按需加载的步骤文档。适合步骤之间强耦合、不需要独立调用的场景。

## 3. 主 Skill 如何编排子 Skill

拆出来之后，主 SKILL.md 要写清楚执行顺序和交接点。

````markdown
## 执行流程

按以下顺序依次执行各子步骤，**每个步骤完成后运行其验证命令确认无误再继续**：

### Step 1: 环境初始化

读取并执行 [环境初始化](steps/00-environment-setup.md) 中的所有步骤。

**检查点**：
```bash
bash scripts/check-env.sh
```

### Step 2: 依赖更新

读取并执行 [依赖更新](steps/01-dependency-update.md) 中的所有步骤。

**检查点**：
```bash
go mod tidy && go build ./...
```

### Step 3: API 迁移

读取并执行 [API 迁移](steps/02-api-migration.md) 中的所有步骤。

**检查点**：
```bash
grep -rn "old-http-client" . --include="*.go" | wc -l
# 预期输出：0
```

## 注意事项

- 如果某个步骤的检查点未通过，**停止后续步骤**，先修复当前问题
- 每个子步骤也可以独立使用，无需跑完整个流程
````

## 4. 拆分的三条原则

**原则一：一个子 Skill 只管一件事（单一职责）**

| 子 Skill | 职责 | 可独立使用 |
|---|---|---|
| `env-setup` | 环境初始化与依赖配置 | ✅ |
| `api-migration` | API 调用层迁移 | ✅ |
| `config-transform` | 配置文件格式转换 | ✅ |
| `test-adaptation` | 测试用例适配 | ✅ |

**原则二：把依赖关系写明白**

子 Skill 之间有先后顺序的，在文档里写清楚，别让 AI 猜：

```markdown
## 前置条件

**⚠️ 重要**：执行本步骤之前，必须先完成 **环境初始化** 环节。

## 相关 Skill

- 前置：[project-migration-sub-env-setup](../project-migration-sub-env-setup/SKILL.md)
- 后续：[project-migration-sub-test-adaptation](../project-migration-sub-test-adaptation/SKILL.md)
```

**原则三：每个子 Skill 都能单独使用**

拆出来的子 Skill 不应该离了主流程就跑不起来。好处：只做部分改造的场景、快速修复特定问题、新项目的增量接入。

## 5. 版本控制

在元数据里标好版本号：

```yaml
metadata:
  author: TeamName
  version: "2.1"
```

| 变更类型 | 版本变化 | 示例 |
|---|---|---|
| 修复问题、补充说明 | 1.0 → 1.1 | 修复某个边界场景的处理逻辑 |
| 新增步骤或场景 | 1.1 → 1.2 | 增加对 gRPC 客户端的支持 |
| 重大结构调整或流程重写 | 1.x → 2.0 | 从单体拆分为模块化架构 |

在 Skill 目录下维护简单的 CHANGELOG，记录每次变更的原因和内容。

## 6. 跨项目复用

做好的 Skill 如果其他项目也能用，同步到用户级目录，所有项目都能享受：

```bash
# 将项目级 Skill 同步到用户空间
cp -rf ./project/.codebuddy/skills/my-skill ~/.codebuddy/skills/

# 或通过包管理器安装社区 Skill
npx openskills install anthropics/skills
```

> 注意：Skill 放的位置不同，生效范围不同——用户级对所有项目生效，项目级只对当前项目生效。不同工具的路径可能不同，以所用工具的官方文档为准。

## 7. 团队协作与分享

Skill 是团队知识资产：

- **像代码一样 Review** —— 新 Skill 或重大修改通过 PR 提交，团队成员 Review 后合入
- **维护变更日志** —— 在 Skill 目录下维护 CHANGELOG，记录每次变更的原因和内容
- **避免冲突** —— 多人编写同一个 Skill 时，按功能模块分工，各写各的子 Skill，最后在主 Skill 中编排
- **定期清理** —— 不再使用的 Skill 及时归档或删除，避免浪费 Level 1 的常驻 Token
- **标明负责人与单一正式版本** —— 给每个 Skill 标明负责人、版本和更新日期，保留一个大家都能找到的正式版本

**创建 / 修改 Skill 时的通用工作约定**（可作为团队默认流程）：

1. 先确定要做什么、触发场景和预期输出。
2. 起草草稿（正文只留执行必需内容，长背景放 `references/`）。
3. 用"正常 / 缺资料 / 不适用"三类任务实测。
4. 根据实测反馈修改措辞或补充示例。
5. 重复 3–4 直到稳定。

分享前检查清单（脱敏与可用性）：

1. 一眼能看懂用途及不适用范围。
2. 所需资料、缺失处理和执行步骤写清楚了。
3. 有明确的交付格式和可核对的完成标准。
4. 用正常、缺资料、不适用三类任务试过。
5. 示例已脱敏，没有密码、密钥或不应共享的客户信息。
6. 已标明负责人，确认同事能找到并使用正确版本。

## 8. 持续迭代优化

Skill 不是写完就不管了。定期打磨，作为资产持续维护：

- **记下哪里出过问题**：AI 跑 Skill 时犯了什么错、偏了什么方向
- **找规律**：同一类错误反复出现，那就是 Skill 写得不够清楚
- **从个案提炼通用规则**：别头痛医头，找到根因再改
- **精简内容**：一句话说清楚的就别写三句

几条实用的改进思路：

1. **从具体反馈中总结规律** —— 别只修一个 case，想想同类问题怎么一劳永逸
2. **越精简越好** —— 多余说明不但浪费 Token，还可能误导 AI
3. **解释原因** —— 让 AI 理解"为什么"，而非死记"怎么做"
4. **发现重复操作就封装** —— 测试时如果每次都要做同样的准备，直接写进 Skill

### 一种高价值的迭代方法

不要凭空想规则，而是让 AI 从你的**真实修改行为**中学习：

1. 用 Skill 让 AI 处理一段真实内容
2. 自己动手修改 AI 的输出
3. 把"AI 的版本"和"你改过的版本"一起发给 AI，问：我改了哪些地方？这些修改背后的规律是什么？
4. 让它把规律总结出来，写进 SKILL.md 作为新增规则
5. 再跑一次看效果，循环重复

每一次修改都代表你的真实偏好，比凭空设计规则靠谱得多。

### 基于反馈的规则补全

当你从反馈中发现某条规则缺失或表述不清时：
- 把该规则**补充/修改进 SKILL.md**（必要时调整它所在章节的位置，把高优先级规则前置）。
- 用**当初失败的那个案例**回归验证一次。
- 若同类问题仍反复出现，考虑是否该把规则改写成检查点或示例，而不只是加一句描述。
