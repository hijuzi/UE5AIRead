### 版本锚点来源：首选 `Build.version`，不要依赖 Manifest

**首选**读引擎自带的 `Engine/Build/Build.version`：

```powershell
Get-Content "E:\EpicGames\UE_5.8\Engine\Build\Build.version" -Raw
```

2026-10-10 实测内容：

```json
{ "MajorVersion": 5, "MinorVersion": 8, "PatchVersion": 3, "Changelist": 58210709,
  "CompatibleChangelist": 55116800, "IsLicenseeVersion": 0, "IsPromotedBuild": 1,
  "BranchName": "++UE5+Release-5.8" }
```

解析规则：版本锚点 = `UE <MajorVersion>.<MinorVersion>.<PatchVersion> (Build <Changelist>)`
→ 本机为 **`UE 5.8.3 (Build 58210709)`**。

**为什么不用 Manifest**：它会漂移。2026-10-10 重装 UE 5.8 后，Manifest 里该引擎的条目**直接消失了**
（只剩同为 `E:\EpicGames\UE_5.8` 路径的 `FabPlugin_5.8` / `QuixelBridge_5.8` 等**插件**条目）。
用 Manifest 查会得到空结果，而"空结果"很容易被误当成"命令写错了"而不是"数据源不可靠"。

**引擎身份只认版本号，不认文件时间戳（mtime）**：重装或整目录复制会让整棵源码树的 mtime 整体漂移
（实测：一次重装即可让 6.5 万个文件的 mtime 全部落进同一个二十来分钟的窗口内），
mtime 既不能证明"被误改"，也不能证明"未被误改"，**不作为判据**。
`ue-doc-verify` 已改为实读 `Build.version` 核对版本号（2026-10-11）。

Manifest 仅作**备用**来源（必须带 `-Encoding UTF8`，否则报 `无效的 JSON 基元`）：

```powershell
Get-ChildItem "$env:ProgramData\Epic\EpicGamesLauncher\Data\Manifests\*.item" |
    ForEach-Object { Get-Content $_.FullName -Raw -Encoding UTF8 | ConvertFrom-Json } |

```

## 二、路径规范

**统一规则：文档中所有引擎路径一律相对 UE 安装根，一律以 `Engine/` 开头，使用正斜杠，不含盘符。**

| 写法 | 结论 | 示例 |
|---|---|---|
| 相对安装根（引擎） | ✅ 采用 | `Engine/Source/Runtime/Core/Core.Build.cs` |
| 相对安装根（插件） | ✅ 采用 | `Engine/Plugins/EnhancedInput/Source/EnhancedInput/EnhancedInput.Build.cs` |
| 相对 `Engine/` | ❌ 禁止 | `Source/Runtime/Core/Core.Build.cs` |
| 绝对路径 | ❌ 禁止 | `E:\EpicGames\UE_5.8\Engine\...` |

这样处理的收益：换机器、换引擎版本时路径依然成立，且不同产物的交叉链接不会因环境差异而断裂。

## 四、引用格式

正文中引用引擎代码时，统一用下面的块：

```
文件：Engine/Source/Runtime/Core/Public/CoreTypes.h
行 14-44：FName 类定义
```

规则：

- `文件：` 后跟相对安装根的路径（见第二节）
- `行 A-B：` 后跟该区间内容的简短说明
- 行号必须是**实际核对过的行号**；`ue-doc-verify` 会逐条回查，对不上的必须修正
- 一个引用块只描述一处代码，多处引用写成多个块

> **命名空间与宏不要臆造。** 本版引擎的 `UCLASS` 类定义在头文件中通常带 `ENGINE_API` 或
> 模块导出宏，写文档前先读原文件确认，不要按"常见写法"推断。

### 4.1 机器解析的三条规避（必须遵守）

`ue-doc-verify` 的 `verify-refs.ps1` 按 **token 边界** 解析引用；以下三类写法会被误判为"引用缺失"，
在批量轮里反复复发（见 `_meta/quality-report.md` 第七节），写产物时必须规避：

| # | 错误写法 | 后果 | 正确写法 |
|---|---|---|---|
| 1 | 模块内相对形式，如 `Engine/Classes/...`、`Public/...` | 按安装根拼接 → 文件不存在 | 补全到安装根：`Engine/Source/Runtime/Engine/Classes/...` |
| 2 | 用 `.../` 缩写中间段 | 缩写段不能解析，同上 | 写完整路径，不省略中间段 |
| 3 | 路径后紧跟全角括号或中文、没有分隔 | 全角括号被并入引用 token | 路径与后文之间留空格，或用反引号包裹路径 |

> 第 3 条的依据：块形式的路径 token 取「非反引号、非空白」字符，故空格、换行、反引号是有效分隔符，全角括号不是。

**适用范围（回避误伤）**：本节约束的是**引用**——即 `文件：…` 块与行内 `<名>.h 行 N` 两种形式。
以下两类文本**不受本节约束**，扫描时不应计为违规：

| 类 | 形态 | 位置 |
|---|---|---|
| 历史叙述 | 记述旧写法本身，如"（`Engine/Classes/...` 形式解析失败）"、"（`…/` 缩写 → 全文）" | 产物末尾「更新记录」节 |
| 目录树注释 | 代码块内的文件名 + 全角括号标注，如 `Constraint.h（19.22 KB）`、`Classes/（HandlerComponentFactory.h …）` | `modules/*-结构.md`「二、目录结构」节 |

> 判据：`verify-refs.ps1` 的解析器只读 `文件：` 块与行内形式，这两类文本不构成引用 token。
> 真正会踩第 3 条的是**引用块内**的"路径后紧跟全角括号"（第四批已修 4 处）。

### 4.2 计数类断言必须可复算

产物里出现「**N 处 / N 个 / N 行 / N 命中 / N 文件**」这类**数字断言**时，只给数字不算完成——
必须同时给出**能跑出这个数字的命令与范围**，否则该数字既无法复核，也看不出**口径漂移**。

| 要求 | 说明 |
|---|---|
| 位置 | 每篇产物末尾必须有 `## 取数说明` 节，表头固定为 `| 断言 | 取数方式 |` |
| **覆盖** | **正文中每一个计数断言都要在该表里有一行**；查不到对应行的数字视为不合规 |
| 四要素 | 每行的"取数方式"必须写清：① 数的对象（哪个文件 / 哪棵树）② 匹配模式 ③ 是否区分大小写 ④ 递归还是仅顶层 |
| 基准 | 命令的相对基准统一为 `Engine/Source`（与第二节一致），命令用反引号包裹 |
| **结果** | 命令的实际执行结果必须与断言里的数字**一致**——`ue-doc-verify` 会实际跑一遍比对 |
| **方法标记** | 每行"取数方式"**必须以 `[M]` / `[R]` / `[H]` 之一开头**（见 4.2.1）；无标记的行**视为不合规** |

**为什么立这条**（2026-10-11 语义轮实测）：该轮约 **1,800 处核对点**中，**行号类**只错 **9** 处，
而**计数类断言错了 13 处**（26→38、20→37、9→8、9→10、0→11）。
差别不在"看错"，而在数字没把口径写进命令里。

> 措辞更正（v1.6）：原文写"约 1,800 处**行号引用**"，实为**核对点**——两者是**包含关系**
> （该轮核对点总数约 1,860，行号类是其中一个子集）。三个口径的区分见 4.4。

典型反例：`types/FGameplayTag.md` 原写"全文 `virtual` 全匹配 **0** 处"——实际该文件有 **11** 处 `virtual`，
全部在别的类型内。结论（本类自身无虚函数）是对的，但那个 `0` 暴露了口径已从"本类"漂到"全文"。
若当初附上命令与范围，这一类错误在产出时就会自己暴露。

#### 4.2.1 方法标记：把"不可复算"变成显式声明

要求每行取数方式给出**可执行命令**，在实操中撞上一个硬边界：**大量计数天然无法机器复算**——
"类内 is 段 **12** 条"这类数字只能**逐行通读**得出，写不出命令。

若不处理，这些行就会**悄悄从检查里漏过去**（检查器只报"跳过 N 行"，无从判断跳过的该不该跳）。
因此本规范要求：**每行必须显式声明自己的方法类别**，把"不可复算"从**默认状态**变成**需要声明的例外**。

| 标记 | 含义 | 该行必须满足 | 检查器行为 |
|---|---|---|---|
| **`[M]`** | 机器可复算 | `取数方式` 内至少含一条**白名单形式**的可执行命令 | **实际执行**，结果须与断言数字一致；无命令即判 FAIL |
| **`[R]`** | 引用型（数字取自其他产物） | 写明来源路径（反引号包裹） | 校验来源存在；数字本身不在本机重算 |
| **`[H]`** | 人工通读型 | 写明**通读对象**与**判据** | 不做机器复算；其中形如引擎文件路径的反引号 token 须存在 |

标记写在 `取数方式` 单元格**开头**，形如 `` `[M]` 引擎磁盘递归计数：… ``（可带反引号包裹，便于阅读）。

白名单命令形式**仅此三种**（避免文档变成任意代码执行面）：

| 形式 | 用途 |
|---|---|
| `(Get-ChildItem "<路径>" [-Recurse] [-File] [-Filter *.x]).Count` | 文件 / 目录计数 |
| `[System.IO.File]::ReadAllLines("<路径>").Count` | 单文件行数 |
| `Select-String "<路径>" -Pattern '<模式>' [-CaseSensitive] -AllMatches [-Range A-B]` | 单文件模式命中数；`-Range A-B` 把计数限定在 A–B 行内（**"类内 / 结构体内"口径必须用它**） |

- 路径相对 `Engine/Source`；以 `Engine/` 开头者相对安装根。
- **只支持单文件模式计数**：跨文件搜索（如"全树 0 命中"）不能写成白名单命令 → 归 `[R]` 或 `[H]`，不得伪装成 `[M]`。

### 4.3 行号引用的合法形式（写法要求）

正文中指向"某文件某行 / 某行段"时，**只有下面三种写法被承认**。其余写法机器无法把它绑定到文件——
既不能校验文件是否存在，也不能校验行号是否越界。

| # | 形式 | 例 | 机器可绑定 |
|---|---|---|---|
| 1 | **块式** | `文件：Engine/Source/…/X.h` 换行 `行 14-44：说明` | ✅ 全部 |
| 2 | **行内式（名在前）** | `` `X.h` 行 14-44 `` | ✅ 全部 |
| 3 | **行内式（数字在前）** | `` `X.h` 第 14-44 行 `` | ✅ **仅当文件名紧邻数字**（中间只允许空格、反引号、一个左括号） |

**不承认的写法**（机器一律计为 unbound：不复算、也不报错）：

| 不承认 | 原因 |
|---|---|
| `（第 39 行）`——文件名在别处 | 本行的邻接范围内没有文件名。实测**"靠上下文推断"不可靠**：同一行常引用多个文件（`modules/Renderer-结构.md` 有一行并列 4 组），同一段落常有多个候选（一张 API 表就是一个段落） |
| 一个引用块混写多个文件的行号 | 绑定歧义，无法判定每个行号属于哪个文件 |

**为什么必须收紧**（2026-10-15 实测）：全库行号引用 **2,058** 处，其中机器可绑定 **514** 处（**25.0%**），
其余 **1,544** 处因上述写法落在检查之外。写成合法形式后，新产物的机器覆盖可趋近 100%，
**且不需要检查器去猜**。

> 收紧而不是放宽的理由：放宽只能靠启发式绑定，而启发式绑定会**造出假 FAIL**——
> 实测把"同段落恰有一个文件名"当依据时，抽查 4 例全错（表格整表一段、正文与说明同段、
> 一行并列多文件、文件名在别行的情形都会被误绑）。**假 FAIL 比不检查更坏**：
> 它会诱导人去"修正"本来正确的产物。

### 4.4 行号引用的三个口径（勿混用）

「行号引用有多少处」这个问题有**三个互不相同的口径**，历史上曾因混用产生误读。
引用数字时**必须写明用的是哪一个**：

| 口径 | 定义 | 当前值 | 取数方式 |
|---|---|---|---|
| **行号引用总数** | 正文中所有指向"某文件某行 / 某行段"的表述（`行 N` 与 `第 N 行` 两种写法都算） | **2,058** | 见下方命令块 |
| **机器可绑定** | 上述之中，检查器能绑定到文件并校验越界（含文件存在性）的部分 | **514**（25.0%） | `verify-refs.ps1` 的 `[4] … resolved points`；分项 `by kind` = `block:158 inline:46 di-name:116 di-path:194` |
| **语义核对点** | 人工抽样、逐条**打开源码比对内容**的项（含行号类、计数类、枚举类、归类判断） | **≈1,860**（2026-10-11 轮，每篇约 27 处） | `_meta/quality-report.md` 第九节 9.1 |

取数方式（行号引用总数，`Engine/Source` 无关，直接对 `docs/` 统计）：

```powershell
# 「行 N」写法 → 302
(Select-String -Path "docs/modules/*.md","docs/types/*.md","docs/flows/*.md" -Pattern '行\s*\d' -AllMatches).Matches.Count
# 「第 N 行」写法 → 1,756
(Select-String -Path "docs/modules/*.md","docs/types/*.md","docs/flows/*.md" -Pattern '第\s*\d+\s*[-\u2013~]?\s*\d*\s*行' -AllMatches).Matches.Count
```

> 三者的关系：**语义核对点**是**人工抽样**的、**跨全部断言类型**的核对项（其中行号类约 1,800 处）；
> **机器可绑定**是**机器全量**能校验的行号引用。前者靠人、后者靠脚本，
> **不可互相替代，也不可直接比大小**。

## 六、目录与命名

| 目录 | 内容 | 生产者 | 命名规则 |
|---|---|---|---|
| `docs/_meta/` | 元信息 | 主技能 / 盘点 / 校验 / 评估 | `convention.md`、`inventory.md`、`engine-modules.json`、`quality-report.md`、`skill-suite-assessment.md` |
| `docs/modules/` | 模块级结构 | `ue-module-structure` | `<模块名>-结构.md` |
| `docs/types/` | 类型级 API 面 | `ue-type-api` | `<类名>.md` |
| `docs/flows/` | 机制级调用链 | `ue-flow-trace` | `<机制名>.md` |
| `docs/ai/` | AI 检索索引 | `ue-ai-index` | `ai-index.md` |
| `docs/` 根 | 全库索引 | 主技能 | `00-索引.md` |

- 文件名用中文（模块名、类名等英文标识符保持原名），便于人工查阅。
- 子文档命名：`<主名>-<子名>.md`，如 `UI模块-框架核心.md`。
- 每份产物末尾必须有「相关文档」小节，列出可交叉引用的其他产物。

## 七、写入边界（红线）

| 规则 | 说明 |
|---|---|
| **引擎源码只读** | 禁止对引擎安装根下任何文件执行写操作 |
| **写入仅限 `docs/`** | 产物路径由第六节固定，不得写到技能目录或仓库其他位置 |
| **不修改已有产物的事实内容** | 补充与修正在原文上叠加；修正历史留痕，见第八节 |

---

## 八、校验状态与修正留痕

- 产物创建时 `校验状态：未校验`。
- `ue-doc-verify` 核对通过后，回填 `校验状态：已校验（YYYY-MM-DD）`。
- 内容发生实质修正（不只是错别字）时，在产物末尾追加：

```markdown
## 更新记录

- 2026-10-12 修正 Uxxx 的行号引用（原 88-102 -> 实际 91-105）
```

- 只做补充、未改事实的更新，可不记入更新记录，但要刷新「生成时间」。
