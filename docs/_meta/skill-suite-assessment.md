## 四、横向发现（本报告最重要的部分）

### 4.1 "修正传播不完整"——套件级过程缺陷（P0，本轮修复）

同一个模式在本套件已出现**四轮**：

| 轮次 | 修正了什么 | 漏掉的传播 | 何时暴露 |
|---|---|---|---|
| 1 | 设计 §12.1 修正"300 量级"检查点口径 | ① 的完成检查副本 | 本轮评估 |
| 2 | §15 复核更新 `convention.md` 上半部「源码形态」 | 同文件下半部"调用链 ❌ 不可行" | 实跑 ④ 时（§16.3） |
| 3 | ⑤ 首轮修正产物 `377→376`、`AutoRTFM 两次→3 次` | ② 的 SKILL.md 正文本地副本 | 本轮评估 |
| 4 | ⑤ 首轮修正派生口径"三张表" | ② 的完成检查副本 | 本轮评估 |

**根因**：修正动作是"就地改一处"的，缺少"全库检索同一事实的所有副本"的步骤。
**本轮落实的修法**：修正后执行反向检索（对 `300 量级`、`377`、`AutoRTFM`、`.\scripts\` 四组旧值全库 grep，
确认技能目录已清零，仅设计说明的历史记录小节保留——历史记录属预期的留痕）。
**建议固化**：以后每次修正"可检索的事实"（数字、路径、口令词），把"反向检索旧值"作为修正流程的最后一步。

### 4.2 触发矩阵（静态分析）

| 风险对 | 评估 |
|---|---|
| ② vs ③ vs ④ | 产物粒度词（模块/类/机制）区分清晰；互相在 description 里写了替代路径；**混合表述**（"分析 Core 模块里的 AActor"）无专门规则——低风险，由主技能路由兜底 |
| ③ vs ④ | "生命周期钩子"边界写了两处：③ 只写"何时被调用"、④ 写完整链 |
| ⑤ vs 生产技能 | "校验/核对/回查"语义独立，未发现冲突 |
| 主技能 vs 子技能 | 主技能 description 已声明"用户已指明具体模块/类/流程时交由对应子技能"，示例 2 演示了不抢活 |
| ① vs `epic-engine-inventory` | 双向声明；职责正交（装在哪 vs 有哪些模块） |

**结论**：静态看无高危抢触发；但**无实测数据**，见 4.3。

### 4.3 评估用例未持久化（P1）

skill-authoring 要求 `evaluation/trigger-cases.md`（正例 10–20 / 反例 10–20 / 边界若干）与
`quality-cases.md`（输入 + 评分标准），且设计说明 §11.1 自己也有"三类任务（正常/缺资料/不适用）验收"的
未勾项——**两个要求是同一件事，至今未落地**。6 个技能目录均无 `evaluation/`。

### 4.4 脚本调用路径基准（P1，本轮修复）

本套件的实际执行 cwd 是仓库根；主技能与 ① 原先写 `.\scripts\xxx.ps1`（技能目录基准），
在无额外说明时会解析到"仓库根/scripts"而失败；而 `convention.md` 与 ⑤ 用仓库根相对全路径并已实跑成功。
本轮统一为仓库根相对写法（5 处命令）。
> 附加观察：同仓库的 `skill/tool/epic-engine-inventory` 仍是技能目录基准写法，不在本套件范围，是否统一由用户决定。

### 4.5 Level 1 常驻开销核算（设计说明 §11.1 待办，本次补）

6 个技能 × 约 80–150 token ≈ **500–900 token 常驻**。若 ⑥⑦ 落地，8 技能 ≈ 700–1,200 token。
